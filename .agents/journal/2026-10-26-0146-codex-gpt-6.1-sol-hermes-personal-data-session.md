## Зроблено

Створив FirebaseSessions для майбутнього читання щоденника з Hermes Desktop без відкритої вебвкладки. Це звичайна користувацька Firebase-сесія, технічно з правами цього користувача за Firebase rules. Продукт передає її тільки фіксованому Node reader; native профіль, модель та Desktop секрету не отримують. Не називаю цей grant криптографічно read-only. Кожний UID має окрему зашифровану базу з відокремленим purpose/AAD; дружині не потрібен ChatGPT-акаунт.

Перед прив’язкою перевіряються bearer JWT та результат обміну refresh token: підпис чинним Firebase authenticator, issuer, audience та той самий UID. Токени не повертаються в UI/помилки. Обмін серіалізований, pending фіксується до зовнішнього POST; невизначеність блокує повтор старого ланцюга. Є окреме від’єднання та повне закриття обох сховищ навіть за помилки одного.

Gateway передає свій verifyTurn до кожного native model callback через verifySnapshot. Порожній adapter hook більше не може пропустити dayProof/contextRevision. Свіжі дані перевіряються до й після модельної відповіді.

## Перевірки

16 Firebase/vault і8 personal Gateway тестів пройдено. Канарки: чужий UID/підпис, шифрування, purpose isolation, конкурентний refresh, невизначена ротація, збій checkpoint перед повторним connect, помилка першого vault при закритті другого, stale snapshot у model callback. Реальних HTTP/model/STT запитів0.

Незалежне рев’ю personal_local_review підтвердило два P2: exchange до перевірки pending та неповне пакетне закриття. Обидва виправив, додав регресії, остаточний PASS без відкритих P1/P2. Вузький verifySnapshot diff також PASS.

Документацію взяв з https://firebase.google.com/docs/reference/rest/auth#section-refresh-token та чинного workers/meal-parser/src/auth.js. Context7 недоступний через вичерпану квоту. Firebase може повернути той самий або новий refresh token; project_id у прикладі числовий, тому звіряю справжні JWT issuer/audience/UID, а не рядок project_id.
