## 0. Node перед сервером

Історична база й попередні CI використовували `.nvmrc = 24.11.1`; під час погодженого етапу 0 репозиторій оновлено до 24.22.1. [Офіційний security release 21.10.2026](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) містить виправлення високої серйозності для гілки 24; рекомендована точна версія [24.22.1](https://nodejs.org/en/blog/release/v24.22.1). Не встановлювати 24.11.1 на production.

Для оцінки сумісності окремо розпаковано офіційний Node 24.22.1 без зміни системного runtime або `.nvmrc`: 8/8 перевірок упакованого API та 47/47 серверних тестів успішні. Це не замінює Linux/systemd і повний CI нового SHA.

Після погодження: знайти всі pins у `.nvmrc`, CI та Linux fixtures; оновити їх узгоджено без переходу на інший major. Запустити app/Worker/storage/server/rules/phone-lab, реальний systemd із синтетичними credentials та браузерні сценарії. Класифікувати 99 advisories кореневих залежностей за фактичною досяжністю у браузері, збірці та сервері; нерозібраний або досяжний дефект високої серйозності блокує B. Виправляти лише підтверджені проблеми мінімальним reviewed diff, без npm audit fix --force чи міграції фреймворку. Новий SHA, CI run, SHA256 пакета та Node обов’язкові в install record. Якщо змінюється продуктова поведінка, модель, ресурси або контракт бюджету, це окреме рішення. Підготовлені архіви 24.11.1 є тільки історичним доказом, у майбутню install-команду їх не підставляти.

## A. Передумови, які поки не доведено

Попередня приватна інвентаризація є історичним знімком від 22.10, не поточним станом. Цього разу сервер не опитувався. В `release-manifest.json` серверні поля залишено `null`.

Якщо потрібен ACCESS-01, використати лише окремо погоджений тимчасовий доступ і старий read-only script SHA256 `7640e81cc12cd886aec8d48c31cd6d936c072f8fecd12114d4b27733d600bd63`. Імена, IP, user ID та результати тримати лише в приватному runtime.
2. Звірити порт 8787, відсутність конфліктних `/opt/scisense`, service/user і state, вільні ресурси, версію systemd та `systemd-creds`. Конфлікт не перезаписувати, інший порт не вигадувати.
3. Визначити реальні vhost/listener/config paths OLS, Unix-користувача OLS, керування конфігурацією через xCloud та доменний scope SSL. Не переносити guessed paths у sudo-команди.
4. Зафіксувати існуючі маршрути/сертифікати/сусідні сайти. Прочитати metadata наявних backup, локально скопіювати цільові конфігурації й rules, перевірити перелік/хеші та відновлення у приватну локальну теку. Створення серверного snapshot/export або будь-який remote write належить B. Backup тільки з повідомленням «успішно» недостатній.
5. Звірити Firebase authorized domains, правила/індекси та обсяг legacy-зв’язків тренера без виводу приватних прийомів їжі. Особисті дані у звіти/публічний Git не копіювати.

Етап A сам не дозволяє встановлення. Якщо A погоджено без B, після інвентаризації зупинитися та відкликати тимчасовий доступ.

## B. Порядок встановлення без model API

1. Затвердити install record: кінцевий SHA/архів після етапу 0, Node/архітектура, hash preflight, точні файли OLS і rollback backup. Виконати передопераційні HTTP-перевірки сусідніх сайтів; не збирати cookies/персональні сторінки.
2. Створити окремого системного `scisense` без login shell. Файли релізу та Node належать root; стале сховище сервісу обмежене `/var/lib/scisense`, тимчасові файли ізольовані `PrivateTmp`. Реліз `/opt/scisense/releases/<SHA>`, Node `/opt/scisense/runtimes/node-v24.22.1-<arch>`, симлінки `current` і `node`. Окремий root-owned `/opt/scisense/public` спочатку вказує на `releases/<SHA>/maintenance`. Лише після writer fence він атомарно переключається на `build/`; корінь payload із server/config/node_modules ніколи не є webroot.
3. Передати готовий архів і один перевірений Node archive; звірити SHA256 до розпакування, всі payload-хеші після. Не виконувати `npm install`, збірку або випадкові завантаження на сервері. Не змінювати системний Node/PM2 чи сусідні сервіси.
4. Встановити лише базовий `scisense-api.service`, перевірити `systemd-analyze verify`, daemon-reload і запуск. Немає `50-live.conf`, activation receipt, credentials або SQLite budget. StateDirectory може створитися порожньою. Перевірити health на `127.0.0.1:8787`: 200, `inferenceEnabled:false`, socket тільки loopback, UID/права/ліміти фактичні. Unit має `Restart=no`: автоматичного відновлення після збою процесу немає. Увімкнення при старті ОС допускається після цих перевірок; це не crash restart.
5. Додати окремий static vhost `ntzg.pp.ua`: document root `/opt/scisense/public`, який поки вказує на maintenance; API proxy на `127.0.0.1:8787`, prefix `/meal-api` збережений, без SPA fallback для `/meal-api/*`. Proxy timeout ≥70 с, retry 0, response buffering off; розмір тіла 15 MiB. Для API та `/index.html`/HTML: no-store і обхід кешу Cloudflare; для hashed `/static/*`: довгий immutable cache. На невідомий API path потрібен JSON 404, не index.html.
6. TLS: тільки ntzg, чинний Cloudflare proxy; запропоновано Origin CA на 1 рік та Full (strict) лише після перевірки chain/hostname. Приватний ключ через захищений stdin/secret store, не в Git або argv, цільовий файл root600. Не змінювати SSL інших доменів чи спільний listener без конкретного дозволеного diff. Якщо zone-wide Full (strict) зачепить інші hostname, потрібне правило тільки для ntzg; за його недоступності зупинитися. Origin CA не призначений для прямого обходу Cloudflare. [Cloudflare documentation](https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/).
7. Спочатку конфігураційна перевірка OLS, потім один контрольований graceful reload. Повторити свої й сусідні HTTP-перевірки. Якщо xCloud не підтримує цей scope або перезаписує proxy, зупинитися, а не обходити панель неперевіреною глобальною правкою.
8. Додати ntzg у Firebase authorized domains, зберігши інші. Клієнт використовує `signInWithPopup`, authDomain лишається чинним; не вигадувати redirect proxy. Перевірку Google-входу виконати тільки після кроку 9, з урахуванням обмежень popup. [Firebase reference](https://firebase.google.com/docs/auth/web/redirect-best-practices).
9. Узгодити коротку перерву запису: спочатку опублікувати нові Firestore rules з writer fence, перевірити заборону старої мутації та дозволений новий writer на погоджених контрольних даних; до успішної перевірки залишати maintenance. Потім атомарно переключити root-owned `/opt/scisense/public` на `releases/<SHA>/build`, перевірити index/asset hash і відсутність застарілого кешу. Лише тепер виконати Google-вхід із кроку 8. Це переключення symlink не змінює OLS-конфігурацію і не потребує другого reload; підтримку такого docroot підтвердити в A. Старий Firebase Hosting автоматично не видаляти. Без цього старі вкладки можуть втрачати нові поля. Legacy-згода тренера не створюється від імені користувача, G04 перевіряється до приватного пілоту. [Контракт переходу](../../WRITER-TRANSITION.md).
10. Зафіксувати live HTTP/headers, allowlist/disabled state, commit/rules release, unit config і backup ID без секретів. Чистий мобільний вхід не доводить готовність голосу; C ще попереду.

## C. Окрема активація та телефон

Перед C потрібні: явний дозвіл на модельні ключі й використання наявного залишку $5, актуальні Free/ZDR і ціни, погоджений UID, один ledger/proposal, точний production release. Не додавати нові $5, не скидати reservation або local transfer marker.

**Окрема технічна передумова:** поточний `transfer-cli send` виконує remote receive напряму, а receiver потребує root. Звичайний admin SSH + можливість sudo цього не доводять. Перед C підтвердити вже погоджений root command transport з pinned host key. Якщо його немає, окремо підготувати й перевірити вузький forced-command/sudo adapter лише для receive-check/receive/status; не вмикати необмежений root SSH і не міняти глобальний SSH самовільно. Поки цього немає, C заблокований, навіть якщо B успішний.

Потім за [BUDGET-TRANSFER](../../BUDGET-TRANSFER.md): спочатку зупинити **лише** `scisense-api.service`, перевірити `LoadState=loaded` і `ActiveState=inactive`, виконати `receive-check --approved-transfer` через підтверджений root transport. Невдалий check зупиняє процес ДО локального export і його постійного fence. Лише після цього зупинити локального writer, експортувати наявний ledger із requireExisting, зафіксувати постійний fence, передати stdin-only, отримати й звірити ack/receipt/rows/consumed/reserved. Після втрати ack читати receiver status, не повторювати імпорт навмання. Часткова передача закриває API до звірки. Імпорт зберігає root/service ownership та шифрує credentials для systemd на хості.

Лише після збігу proposal/configHash/UID/release/receipt/ledger: встановити live drop-in, атомарно активувати manifest і запустити сервіс. Початковий контрольний сценарій: короткий голос + фото, звірити транскрипцію/порцію/БЖВ, додати один раз, перезавантажити й переконатися, що прийом один. Усі витрати входять у той самий залишок $5. Потім Юрій повторює з телефона через мобільний інтернет із вимкненим Mac.

## Відкат і умови зупинки

- До будь-якого production write: backup потрібних файлів/конфігурацій, перевірений restore, запис очікуваного diff. Якщо цього немає, встановлення не починається.
- Неправильний host/hash/архітектура, конфлікт service/path/port, невідомий платіж, брак ресурсу, некоректний TLS, сусідній HTTP regression або несподіваний privilege scope зупиняють етап.
- Відкат першого релізу: зупинити лише SciSense API, вимкнути його live drop-in, атомарно переключити `/opt/scisense/public` на включену maintenance-сторінку або попередню безпечну статичну конфігурацію, перевірити TLS/OLS і сусідні сайти. Не вбивати процеси за загальною назвою та не рестартувати весь сервер.
- Після публікації writer fence не відновлювати старі незахищені rules. Після C не відновлювати старий SQLite, не повертати витрачений бюджет і не запускати стару локальну лабораторію. Відкат коду не є відкатом обліку коштів або згоди.
- Після операції прибрати лише створений тимчасовий SSH-доступ і transient bundle, перевірити відкликання. Зберегти придатний rollback record та encrypted backup за погодженою політикою.
