## Результат для власника

Поточна сесія створює тільки документи, докази читання та журнал. Пряме «погоджую план» дозволить наведені нижче локальні кроки 0–6 з підставними модельними відповідями, demo Firebase та комітами. Двигун: послідовна локальна реалізація з контрольними перевірками. Не потрібні фоновий /goal, нові залежності, міграція фреймворку або кілька паралельних виконавців. Незалежні рев’ю читають тільки потрібні файли, без приватного щоденника. Код не починається в цій сесії.

### 4. Необов’язкова літера у прев’ю та атомарний запис

Модель: Codex; високий ризик гонок Firestore й pending-операцій. Окреме незалежне рев’ю цього блоку.

`ClientApp.js` передає потрібний snapshot плану/дня у VoiceInputModal. Компактний badge відкриває optional редагування, без додаткової обов’язкової дії у звичайному сценарії. Unknown allocation не входить до blocking `itemProblems`; невідомі нутрієнти лишаються помилкою їжі. Ручний вибір, фото й перерахунок застосовуються до одного itemId. Для планової невизначеності показується пояснення, а не помилка збереження.

`mealCommands.js` додає `appendAllocated` для одного обраного прийому з різними групами. `mealStore.js` перевіряє весь пакет і fingerprint проти свіжого root; appendAllocated не додає expectedRevision, щоб інша їжа чи metadata не блокували додавання; marker ідемпотентності має пріоритет. Жодних кількох append у циклі, whole-day replace, нових ID всередині retryable callback або зміни metadata. У `useMealDay.js` та `saveError` визначений stale-plan/revision-conflict звільняє pending для перечитування і нового підтвердження також у чинних quantity/remove/replace; unknown зберігає ту саму команду. Submission_conflict вимагає перечитування без автоматичного нового ID. У ClientApp pending/unknown блокує date/profile та нові записи до retry, закриття модального вікна дозволене; reload hook не стирає команду. Logout не блокувати. Явно перевірити закриття/відкриття, спробу зміни дати та відновлення після визначеного конфлікту. Snapshot змінюється тільки після явного перечитування, не посеред готового save.

`pilotLedger.js` приймає лише три нові числові лічильники з фінального items; без назв їжі, transcript або точних літер. Невизначена літера не робить повний запис їжі partial. Ручний пошук відповідника відмічається окремо від простої зміни літери.

Перевірки L04/L05/L07: дві літери + unallocated в одному пакеті, інша дата/профіль, подвійна кнопка, concurrent append/metadata без зайвого блокування, зміна порцій з перечитуванням, confirmed conflict recovery, unknown після фактичного commit, merge фото, незмінність активності/чужих профілів. Повторити actual-path writer-сценарій кроку 0.

Точка коміту: «feat: зберігати голосові продукти за літерами одним записом».

## Відкат і стоп-умови

Локально кожний блок має окремий commit і негайний push у feature-гілку; відкат через revert, без force-push чи main. До локальних правок резервом служить чистий Git SHA; лише синтетична demo-база. Production backup зараз не знімається, бо сервер не зачіпається.

Схема additive: старі рядки читаються без переписування. До публікації довести old/new actual-path запис. Відкат UI/API може лишити нові поля у даних; старий клієнт має зберегти їх при дозволених операціях. Якщо цього не доведено, відкат вимикає тільки нове додавання до сумісного hotfix, а не повертає backup щоденника поверх нової їжі. Ledger/витрати не відкочуються ніколи. Не відкочувати чинні захисні rules.

Повний перелік стоп-умов цього плану: зміна Firestore rules/IAM або норми харчування; потреба нового бюджету/моделі/додаткового запиту; неможлива сумісність writer; потреба міграції приватної історії; реальна модель/сервер до дозволу; незрозуміла або неатомарна зміна даних. Незалежна локальна робота може продовжуватися, залежний крок чекає конкретного рішення.
