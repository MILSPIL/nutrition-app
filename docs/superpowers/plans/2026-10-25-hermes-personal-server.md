Дата: 2026-10-25, Europe/Kyiv. Статус: погоджено до виконання; незалежне документне рев’ю пройдено.
[Специфікація](../specs/2026-10-25-hermes-personal-server.md). Goal `objective_e45aa8ac1aa3`, G01/G02/G03/G04/G05/G06/G07/G08/G11.

2026-10-25 Юрій прямо підтвердив усі кроки до фінального результату. Локальні0–7, A1–A5 і необхідні наступні B1/B2/B3 погоджені; повторне рутинне погодження не потрібне. Послідовні технічні гейти A0, сумісності, backup та ізоляції зберігаються. Додатковий платіж, автоматична API-заміна чи збільшення ресурсів не дозволені. Продуктове приймання C01–C10/G10 лишається окремим.

## Рекомендований результат

Один серверний оригінал тренера на кожний SciSense-акаунт. Сайт і Hermes Desktop використовують native сесію та пам’ять цього профілю. Налаштоване особисте Hermes-підключення власника обслуговує обидва профілі; дружина входить тільки в SciSense. Модель/провайдер/оплата обираються у Hermes. A0 є технічною перевіркою підключення, без окремої реєстрації SciSense в OpenAI чи листування.

## Крок 0. Контракти, поведінковий red-run і сумісність

Модель: GPT-6.1 Sol, головний агент. Ризик: схеми native історії, невизначені квитанції, auth і Desktop; незалежне рев’ю обов’язкове.

Повний перелік робіт:

1. Зафіксувати SHA застосунку, server pin, schema, Desktop build і несекретну конфігурацію. Не оновлювати чужий Hermes runtime під час дослідження. Сумісність перевіряти на окремому synthetic home.
2. Створити поведінковий harness із двома синтетичними профілями й реальною pinned native authority, підставним Responses-провайдером та двома клієнтами. Запустити C01–C05 на поточній реалізації, отримати FAIL конкретних властивостей. [Структурні FAIL](../../evidence/hermes-personal-baseline-2026-10-25.json) лише вказують місця, не замінюють цей тест.
3. Перевірити resolved named provider `scisense-subscription`, `api_mode=codex_responses`, Responses wire text/image/functions, profile IPC→broker без OAuth у native home. Простий `custom` може демотувати mode, а старий Messages-relay не є реалізацією нового контракту. Підтвердити підтриманий native шлях `session.create/resume`, `prompt.submit`, admission receipt/recovery і під’єднання Desktop. Імена контрактів звіряються з pin; заборонено видавати старий `session.send` за доведений новий протокол або писати безпосередньо в робочу SQLite.
4. Приватна майбутня інвентаризація має однозначно вибрати основну наявну сесію; за неоднозначності вибір власника обов’язковий. На синтетичній історії перевірити native export/import: IDs, повідомлення, дати, батьківські зв’язки, вкладення, repeat skip лише тотожного вмісту. Окремо довести native resume після import, який не переносить живе володіння каналом. Схема32 сама по собі не гарантує сумісності.
5. Скласти технічну A0-квитанцію: вибране Hermes-підключення/модель/транспорт/можливості, авторизація/ліміти й режим обліку. У локальному кроці лише підставні дані; окремий SciSense OAuth-клієнт і звернення до провайдера не створюються.

Додаткова позитивна проба: Desktop input проходить bridge/outbox/dayProof/lease й створює вебпрев’ю через native tool. Перевірити також Unix-socket маршрут за забороненого host-loopback у sandbox і fail-closed memory approval.

Результат: зафіксовані транспортні/імпортні контракти, red-докази й матриця сумісності. Якщо Desktop/pin потребує оновлення або нового протоколу, зупинити цей крок і показати точний додаток до плану. Не форкати весь Hermes для обходу.

## Крок 1. Міст до обраного підключення Hermes

Модель: GPT-6.1 Sol. Ризик: секрети, refresh-ротація, спільна оплата двох профілів.

Повний перелік робіт:

- Відділити `fundingOwner` від `userProfile`. Явна allowlist платника містить лише два підключені перевірені UID. ID/заголовок браузера не може вибрати інший grant, модель чи URL.
- Одне налаштоване власником Hermes-підключення з захищеним серверним credential store; профільні процеси мають вузький IPC-доступ. Реальні секрети не копіюються до контексту дружини чи клієнтів; активний refresh-ланцюг Mac не дублюється.
- Використовувати штатні resolver/auth/client обраного провайдера Hermes. SciSense не реалізує власну OAuth-реєстрацію. Технічна A0 перевіряє фактичну модель/транспорт і можливості на сервері, без припущення, що сама назва в config уже є робочим з’єднанням.
- Серіалізований refresh для одного grant, encrypted atomic commit/fsync та обробка аварії до/після заміни. Невизначений rotation не повторює старий refresh; зрозуміла повторна авторизація. Відкликання одного каналу SciSense не стирає чужі дані; від’єднання спільного платника зупиняє модель в обох профілях.
- Поточний вибір власника GPT-6.1 Sol перевіряється фактичним terminal результатом. Загалом модель/провайдер визначаються Hermes, не константою SciSense. Режим native IPC відповідає вибраному wire; заміна моделі власником не змінює профіль/історію й не запускає автоматичний API-fallback. При вичерпанні доступу лишається ручний трекінг; text-only модель не оголошується придатною для фото.
- Єдиний серверний лічильник усіх provider POST для обох каналів, включно з допоміжними викликами. Облік без текстів/їжі/health; пер-профільний лічильник використання не розкриває повідомлень іншому користувачу.

Результат: локальні перевірки з підставним issuer/provider, підміною токена/UID/моделі/endpoint, refresh-race, quota/error/revoke та невизначеним результатом. Реальний grant не додається.

## Крок 2. Постійні native профілі та спільна історія

Модель: GPT-6.1 Sol. Ризик: два власники одного store, повтори та розділення клієнтів.

Повний перелік робіт:

- Ввести серверний registry `verifiedUID → isolatedProfile → canonicalSession`, без приймання profile/path від клієнта. Окремі OS/HOME/native-store/media/кеш/restore дані.
- Native ingress обох каналів проходить спільний Node admission bridge: durable turn/outbox, глобальна черга, свіжий dayProof, native receipt і lease перед будь-яким tool. Не лишати Desktop поза цим маршрутом. Статус черги лише власний «очікування ресурсу».
- По одному native session owner на профіль. Desktop transport і вузький вебміст надсилають йому команди через перевірений у кроці0 протокол; не створюють незалежних writer-ів до тієї самої SQLite.
- Host-loopback фасад Desktop під SSH пересилає команди через окремий профільний Unix socket у sandbox; host-loopback/internet з agent netns залишаються недоступними. C02 пробує Y→Wsocket та навпаки.
- Прибрати turn-scoped створення/видалення native сесії з нового шляху. Сире медіа прибирається за політикою A4 незалежно від збереження повідомлень.
- Сталий durable outbox UID/profile/session/inputId/payloadHash до dispatch, зі зв’язком admission/generation/nativeMessageId/revision після ACK; прив’язка до профілю/сесії/generation. Повтор після обриву перечитує receipt. Невідоме виконання потребує відновлення, а не нового turn.
- Native історія є єдиним джерелом повідомлень. Локальна SciSense-проєкція відновлюється з неї й містить лише свої app-квитанції/чернетки, не другу редаговану копію чату.
- Один основний діалог; історичні діалоги окремо, явне створення нового. Кеш, фонові запити й незавершені медіа очищуються з клієнтської пам’яті при зміні акаунта без стирання їхнього серверного власника.

Результат: C01/C02 проходять на native fake-provider інстансі після reconnect/restart/двох одночасних повідомлень і відмови сховища.

## Крок 3. Дані SciSense, пам’ять і підтвердження їжі

Модель: GPT-6.1 Sol. Ризик: помилковий день, чужий контекст або подвійний запис.

Повний перелік робіт:

- Персональні норми/програма/виміри за verifiedUID. Забрати спільний DAY_TARGETS як джерело чужих норм; сумісне перенесення чинних норм Юрія без самостійного перерахунку.
- Підставний onboarding дружини, порожня персональна пам’ять, нейтральний coach-template. Реальні дані вводить вона у своєму акаунті через «Профіль і програма»: ручні підтверджені норми без нового калькулятора; порожні норми не блокують облік їжі; наявності сімейного зв’язку недостатньо для доступу.
- Owner-scoped native tools читають живі підтверджені дні/норми/відомі активності. Агрегати рахує код, не модель. Snapshot береться після черги, ревізії перевіряються перед відповіддю й збереженням. Конкурентний Add оновлює проєкції; порада зі старою revision позначається часом і не називає старі числа актуальними.
- Для targetsState unset/partial не генерувати відсутні remaining/progress, 0 або NaN. Усі UI-константи норм у Header/ClientApp/звіті та server snapshot замінюються спільним персональним контрактом; тест після reload обох акаунтів.
- Native memory/context працюють лише у власному sandbox. Дозволені читання свого контексту та зміни власної пам’яті лише через proposal і підтвердження; fail-closed guard проти unconfirmed/missing-module/direct-write, auto-flush вимкнений; той самий native store без дубля contextStore; не вмикати довільні terminal/web/delegate/cron/secret-store tools зі старого профілю.
- Спільні чернетки й idempotent Add використовують чинний SciSense command store. Desktop отримує прев’ю та auth-protected вебпосилання на цю саму чернетку; запис лише по Add з квитанцією.
- Розрізнити snapshot/історію/припущення/оцінку/підтверджений прийом. Детерміновані «сьогодні/вчора» Europe/Kyiv, дата перед Add, одна команда одного дня, збереження historical-day доповнень.
- Великі дні й персональні матеріали мають керовану вибірку та native згортання. Повна приватна пам’ять зберігається на сервері; це не означає відправляти весь архів кожним запитом. Немає мовчазного відкидання обов’язкових фактів чи переписування програми.

Результат: C04/C05/C06, два незалежні набори норм, 20/100 історичних повідомлень, full-day snapshot, midnight/stale/read-failure/replayed Add.

## Крок 4. Засоби міграції та логічного відкату

Модель: GPT-6.1 Sol. Ризик: втрата особистої історії та перезапис нових даних.

Повний перелік робіт:

1. Фіксований операторський інструмент із діями inventory/dry-run/export/import/verify/rollback. Ключі лише stdin або платформний store, без довільного shell/URL і секретних CLI-аргументів.
2. Шифрований bundle лише дозволених матеріалів одного профілю та native export. Окремий конвертер `web-history.mjs` переводить старий SciSense turn-store у native import bundle: стабільні IDs, видимі ролі/текст, походження й fingerprint; round-trip та повторний import перевіряються. Старі tool payload не виконуються як нові команди. Маніфест містить версію схеми/pin, приватні IDs і семантичні fingerprints, вкладення та карту перенесення шляхів. Публічний звіт лише лічильники/verdict.
3. Виключити auth/.env/keychain/tickets/locks/pids/системні hooks/автоматизації й credentials Telegram. Окремо перевірити персональні інструкції як дані; не виконувати їх під час міграції. Активне відсилання Telegram не переїжджає.
4. Імпорт спочатку в порожній isolated store через pinned native export/import. Колізія відмінного вмісту є FAIL. Повторний запуск не створює нових діалогів. Старі web-розмови мають стабільні IDs та окреме походження; unfinished/unknown Add не виконуються повторно.
5. Після cutover source gateway/CLI зупинені, Desktop remote-only. Перевірити, що збій remote не створює локального fallback і source-store не має нових записів. Оригінальні Mac-шляхи перетворити адресним маніфестом на обмежені власні файли й SciSense-інструменти. Незрозумілі залежності призупиняють приватний cutover.
6. Прогнати припинення посеред import, пошкоджений attachment, нестачу місця, інший schema/pin, ID-collision й повтор; підтвердити незмінний оригінал.
7. Логічний відкат після cutover починається із зупинки ingress/завершення або чесної фіксації active/unknown команд. Береться СВІЖИЙ повний export сервера з усіма після-cutover повідомленнями. Повернення здійснюється в новий порожній перевірений native store; overlay старого Mac store не застосовується, бо native import пропускає наявні IDs.
8. Переприв’язка каналу дозволена тільки після звірки хвоста й одного writer. Якщо свіжий export неможливий, не відновлювати стару копію автоматично: зберегти матеріали й показати блокер. Ledger, Firestore, квитанції Add та облік витрат не відкочуються до старого стану.

Старі медіа не очищаються за новою A4 заднім числом; перевищення імпортом фото-квоти блокує приватний cutover до рішення. Відбитки й скасування відповідають явним контрактам специфікації.

Результат: C03/C10 на синтетичних матеріалах. Приватні матеріали користувача в цьому кроці не читаються й не переносяться.

## Крок 5. Месенджер і навігація

Модель: GPT-6.1 Sol. Ризик: зрозумілість станів, телефон, збереження чернетки.

Повний перелік робіт:

- Верхня «Додати їжу» відкриває режим швидкого обліку, плаваюча «Тренер» консультацію. Обидва працюють із власним канонічним профілем, без двох різних тренерів.
- Компактний composer: текст, вкладення/камера/галерея, явний старт/стоп запису, надсилання. Opening не запитує мікрофон і не починає API/запис.
- Дата історії в хедері; вибір дня не підміняє дату нового вислову. Абсолютна дата лишається в прев’ю перед записом.
- Контекстна помилка, черга, quota, auth-required, stale та unknown мають власні дії. Текст збережений; немає неправдивого «перевірте мережу» при іншому збої й двох одночасних alert для однієї причини.
- Перемикання акаунта/сесії/дня під час voice/photo/save не змішує дані. Фото прив’язане до конкретного item; літеру можна виправити без обов’язкового ручного вибору.

Результат: C07 й інваріанти старих voice/photo/add тестів, видимий вибір режиму та особистих норм.

## Крок 6. Перехресні перевірки й негативні сценарії

Модель: GPT-6.1 Sol із незалежним свіжим рев’юером. Ризик: помилка ізоляції або формальний PASS без повного сценарію.

Повний перелік робіт:

- Native synthetic runtime + реальний Desktop із disposable userData/окремим синтетичним підключенням. Робочий Hermes користувача, cookies й профілі для QA не використовувати.
- Два профілі, два канали, рестарт процесу, втрачений ACK, повтор, перехід між акаунтами, паралельні повідомлення, injection спроби дістати інший profile/path/session/media/норму.
- Refresh race/429/401/revoke/stream-failed-after-delta, storage busy/full, profile unavailable, stale revision, malformed one-item і збій одного profile. Другий профіль не отримує чужий fallback і не втрачає дані.
- Перевірити негативні ін’єкції інваріантів C06: неправильна дата, повтор Add, forged receipt, stale snapshot мають падати. Усі TTL/очищення перевірити за відсутності нових запитів, не лише на гарячому шляху.

## Крок 7. Пакети перевіреного встановлення

Модель: GPT-6.1 Sol. Ризик: привілейований хост і приватні матеріали; лише підготовка.

Повний перелік результатів:

- Відтворювані application/runtime пакети з manifests/хешами, pinned dependencies й успішним CI на точному кандидатові.
- Runbook B1/B2/B3 з конкретними шляхами, командами, профільними користувачами/службами, hostname/ports, allowlist операцій sudo й межами доступу. Детальна інфраструктура лише локально.
- Технічна перевірка Hermes-підключення A0, схема encrypted credentials через платформні systemd credentials або рівнозначний перевірений store. Якщо такого store немає, окремий гейт до додавання реальної авторизації.
- План адресної резервної копії та незмінності прийомів/Firestore/ledger, контроль тимчасового адміністратора й його відкликання; приватний контекст не входить у публічний пакет.
- Результати синтетичного native/Desktop тесту, міграції й відкату; таблиця відкритих ризиків. Немає припущення, що SSH-транспорт уже означає працездатний Desktop.

## Реальні B1/B2/B3 після технічних перевірок

Повний перелік дій:

1. B1: read-only inventory актуального хоста, адресний backup і перевірка залишку ресурсів. Нові профільні unprivileged користувачі/служби ізольовані від чинного SciSense й інших сайтів. Лабораторний actual-host canary з fake provider; жодного реального контексту/токена на невдалому canary.
2. Пройти технічний A0 штатного Hermes-підключення. За потреби виконати штатний серверний вхід у вибраний власником провайдер; окремий OAuth-застосунок SciSense не реєструється. Не дублювати активні device-auth токени Mac. Перевірити фактичну модель/можливості/ліміти та encrypted refresh/restart/revocation.
3. B2: перед cutover зафіксувати mapping профілю/активної сесії; призупинити тільки source writer-и цього тренера й його Telegram, зняти фінальний snapshot, шифровано перенести/звірити, під’єднати Desktop. Інші профілі лишаються доступними. Профіль дружини прив’язати лише до її підтвердженого SciSense-входу, без OpenAI-акаунта дружини.
4. B3: один конкретний release/config SHA, перевірки обох каналів і телефона, штатний restart/refresh, зміна акаунта, Mac-off, квитанції Add. Після завершення прибрати тимчасовий admin, перевірити відсутність в API/відхилення SSH і cleanup Keychain. Інші доступи не відкликати.
5. Зберегти зашифровану source-копію неробочою до приймання. У разі невдачі застосувати логічний відкат зі свіжим хвостом, не повертати старий split web/desktop store як нібито ту саму історію.

## Backup і відкат (повний перелік)

- До B1: адресна копія конфігурації/пакета/активного release; жодного глобального restore сервера.
- До B2: зашифрований узгоджений export одного тренера й web-архіву, контроль IDs/вкладень/схеми, копія registry та source fence. Секрети не входять у history bundle.
