# HERMES-COACH-02: наступний етап на погодження

Дата:2026-10-24. Стан: план, не дозвіл на виконання. [Специфікація](../specs/2026-10-24-hermes-coach-next.md).
База86ad3be; готовий локальний HERMES-FOOD-01 використовуємо повторно. Головний пріоритет: прибрати тупик побутової порції й довести до телефона, зберігши просту розмову з тренером.

Для наступного дозволу рекомендовано один локальний пакет: кроки 0–5 + I01, припущення А1–А4 зі специфікації. Це дасть готовий до зовнішньої перевірки кандидат: розмова, порції без ручних БЖВ, автоматичне «вчора», плаваюча «Тренер» і легкі іконки. Приватне перенесення, сервер, реальні API та витрати лишаються окремими B1/B2/C. Історія тренувань і абонементи зафіксовані в черзі наступними.

## Локальні кроки після погодження (повний перелік)

0. Зафіксувати C01–C08 і синтетичні очікування, створити red-перевірки до реалізації. Actual itemProblems/snapshot probe та source-observation відтворені зараз; browser та нові behavior tests повинні впасти на поточному коді. Не брати приватний профіль у fixtures. Модель: Codex, ризик середній; незалежна перевірка еталонів. Commit: контракти/тести.
1. Закрити побутові порції C03. Через наявний food_lookup використовувати перевірену міру з публічного джерела або явну оцінку; короткі size choices у тому самому draft, стабільні item IDs. Не додавати hardcoded точну вагу без provenance. Перевірити одну/дві штуки, зміну розміру, точну вагу, cooked/raw, відсутню міру, недоступне джерело. Дотриматися порядку source/estimate/partial-note зі специфікації: часткова етикетка та конфлікт одиниць не стають повною оцінкою. Не вимагати етикетку; не вимикати валідатор. Модель: Codex, підвищений ризик математики/одиниць; незалежне рев’ю до наступного кроку. Додати явно дозволені food provenance поля і повний resolver→writer→Firestore rules→reload roundtrip, включно partial-note/legacy/невідомими ключами; правила доступу не розширювати. Commit: порції та вузька food schema.
2. Зробити розмовний сценарій C02/C04. Backend формує детерміновані підсумки/частки з чинних сервісів, передає date/revisions/неповноту. Використовувати єдину збережену sentAt для всіх відносних дат і replay; «сьогодні» не стає відкритою історичною датою. Поради не записують їжу, підтверджений Add змінює наступну відповідь. Необов’язкові поля літер згорнуті, результат видимий. Модель: Codex, підвищений ризик stale data; незалежний reviewer перевіряє дату та випадки поради/факту. Окремі red cases: dateContext default/pinned; нова dayRef policy; replay anchor/DST; yesterday preview на непорожньому іншому дні; зміна source identity. Обов’язкові зміни відповідних validators, tools policy, admission/turn-store і snapshot. Commit: advice snapshot та календарний контракт.
3. Додати «Тренер» й відкриття наявного чату C01. Перевірити модалки, keyboard, safe-area, кінець сторінки, повернення фокуса. Швидкі підказки не є другим state machine. Модель: Codex, середній ризик UI; виміряти375/390/1366. Перевірити activeElement не textarea після відкриття; «Записати їжу» лише фокусує введення,0 model calls. Composer date замінюється явним чипом pin, preview date редагується необов’язково. Commit: coach entry.
4. Підготувати локальний контракт curated profile C05: максимум8000 UTF-8 bytes, provenance/покриття/revision, required facts й явний overflow reject. Використати синтетичний великий профіль; жодної правки живого Hermes. Перенесення фактичного приватного пакета тільки B1/B2. Модель: Codex, підвищений ризик приватності та втрати контексту; незалежний reviewer. Встановлення context.txt тільки в API-owned contextStore; pack validator8000/8001, native profile без дубльованих особистих фактів. Позитивний fixture C05 із24 записами/4notes/контекстом8000/історією має пройти чинні32000bytes. Commit: context acceptance.
5. Повна відповідна регресія C06/C07, новий exact SHA, Linux2CPU/2GiB/45с, незалежне приймання, збірка вимкненого пакета. Перевірити очікувані помилки/unknown, а не лише happy path. На новому SHA повторити runtime перевірки, якщо змінені input sizes/adapter/sandbox; незмінні інваріанти підтвердити відповідними suites. Оновити release manifest, журнал і статус; feature commit/push. Модель: Codex + свіжий незалежний Codex reviewer, високий операційний ризик. Продуктовий main не зливається автоматично.

Очікувані змінювані зони після погодження (повний перелік): `src/components/TrainerChat.*`, `src/pages/ClientApp.js`, окремий `TrainerLauncher` за потреби, `server/trainer/{tools,snapshot,gateway,turn-store,drafts,food-resolver,food-lookup,context-store}.mjs`, клієнтські trainerApi/trainerSession/mealItems/foodNotes/mealCommands, вузькі food validators у `firestore.rules`, source manifest/importer лише якщо потрібні household measures, відповідні tests/scripts/docs. Чинні calorie targets, історичні записи, auth schema й глобальний Hermes не змінювати. До правки точний список кожного блока звіряється з red case.

## B1: підготовка конкретного розгортання, окреме погодження

Це одноразовий read-only етап на MS-WEB та локальна підготовка приватного пакета, без server writes/inference. Перевірити поточний release/службу/OS/AppArmor/userns, дозволений SSH transport, вільні ресурси й актуальний ledger metadata; секретні значення не виводити. Попередній Firebase-інцидент залишається відкритим до доказу усунення. Ключі для inference не використовувати.

Приватний пакет формувати локально тільки з погоджених persona/сталих фактів; архів зберегти, не комітити й не індексувати. Показати Юрію приватну таблицю coverage/omissions. Перевірити bytes та source hash, виявити фактичного writer/маршрут Telegram без тестових повідомлень. Поточний огляд не довів живу доставку бота.

Результат B1: точні шляхи/SHA, allowlist приватних файлів, залишок чинного ledger, сумісність host, точний B2/C runbook та rollback. Невідомі значення не підставляти. Host incompatibility зупиняє етап; автоматичного sudo/послаблення/підняття ресурсів немає. Привілейований крок потребує конкретного погодження отримувача/прав/строку.

## B2 та C: межі зовнішнього запуску (повний перелік)

- B2 після окремого погодження точного пакета: зашифровані backups/manifest, перевірений runtime і host rehearsal із synthetic provider, curated profile, новий сервіс та сумісний UI/rules поки вимкнені. Ключі/ledger не копіювати в новий бюджет. Продуктовий merge, якщо потрібний, погодити окремо.
- C після окремого погодження активації та точної вартості: owner-only сайт на ntzg.pp.ua, поточні Groq/Sonnet secrets через чинний encrypted store, один ledger. Спочатку контрольний діалог і телефонний C08 із read-only memory; далі погоджений cutover, лише після нього 7-денний пілот. Підтверджений diary write проходить чинним writer v3; старі нотатки не приховуються.
- Telegram до успішної проби доступний. Після підтвердження Юрія, що вебтренер працює, окремий погоджений cutover саме цього профілю: зупинити admission саме цього Telegram route, завершити його active turns і підтвердити відсутність writer, звірити фінальний source hash/пакет, встановити канонічну revision та увімкнути підтверджені memory updates сайта. Нема паралельних writers одного home.

## Моделі, ресурси й бюджет

Погоджений кандидат: Groq `whisper-large-v3` для голосу та Anthropic `claude-sonnet-5-5` для розмови/фото. Інший provider на Mac не переносимо автоматично; стару авторизацію не використовуємо для сайта. Pin Hermes лишається перевіреним3f2afed; установленний на Mac bf0203a не є дозволом оновити серверний runtime.

Локальна ціль:2CPU/2GiB/swap0, один turn,45с, до3 модельних calls, output4096/call, payload32000bytes. Поточний запис голосу має окремі ліміти. Локальні mocks не витрачають $5. Цей документ не збільшує бюджет і не дає права тестувати real API.

Для C запропоновано переукласти попередні8turns/24calls під нові випадки, у тому самому чинному cap$5, без другого smoke поверх нього: порада за днем; плід без ваги; коротка відповідь про розмір; голос домашньої страви; фото упаковки; уточнення кількості; порада після Add; прохання запам’ятати синтетичне уподобання при read-only memory без food write. Прямий context commit має дати memory_read_only без нового model call. Кількість залежить від залишку й реальних резервів. До дозволу C актуальні тариф, account tier, upper bound у доларах і стан ledger мають бути перевірені заново. Старий розрахунок із попереднього runbook не є поточним дозволом або перевіреним балансом.

## Відкат і приймання

Точки відкату: один commit на локальний блок; початкова база86ad3be, кодce62052. Прапорець launcher/chat задається під час build: потрібні дві перевірені збірки on/off; це не миттєвий runtime toggle. Відкат перемикає release на сумісну збірку з видимими notes. Після запису notes не відкотитися до UI, що їх приховує. Спершу закрити нові admission, завершити/позначити unknown, зберегти актуальні receipts/ledger/context revision; лише тоді перемикати release. Витрати/підтверджена їжа не відкочуються старою копією.

На телефоні Юрій перевіряє одну послідовність: відкрити тренера → запитати пораду → повідомити побутову порцію голосом → одне уточнення або явна оцінка → готові літери/ккал → одна «Додати» → reload → тренер враховує запис. Нема запиту упаковки звичайного плоду чи ручного БЖВ. Далі фото та Mac-off. ПілотG09 і кінцеве G10 залишаються окремими прийманнями, локальний PASS їх не закриває.

## Доповнення черги від Юрія

Автоматичні історичні дати й компактний календар включено у кроки 2/3 та перевірки C02/C08. Оптимізацію зображень оформити окремим вузьким блоком: оптимізовані versioned assets, перевірка вигляду й повторного завантаження без зміни глобального server cache. Історія тренувань/басейну та абонементи потребують окремої специфікації з операціями додавання/виправлення/скасування, журналом відвідувань і точним доступом тренера; їх не включено потай у погодження першого запуску чату. Цей план враховує дві spec-проби й звірку Claude; коду не змінено, документне приймання пройдено.

| Заміна всіх малюнків новими піктограмами | Мінімальний трафік | Непотрібна зміна погодженого вигляду |

Майбутній локальний блок I01 після окремого погодження або включення до погоджених 0–5: виміряти найбільший display box, зробити WebP із запасом для DPR3 (попередньо 192×192, уточнити за фактичним box), зберегти вихідні оригінали, переключити CATEGORY_ICONS на build imports. Якщо якість не проходить, підняти локальний розмір і показати tradeoff, не публікувати зіпсоване. На live перевірити versioned URLs + cache headers після окремого дозволу deployment. HTML та API cache не змінювати.

## Наступна окрема специфікація активності

Послідовність: спершу харчування/тренер/дати, далі структурована історія залу та басейну, потім необов’язкові абонементи. Історія тренувань мусить мати власні stable IDs, часову зону, draft→confirm→receipt, idempotent append/edit/delete, невідомі поля без вигадування й огляд попередніх занять у trainer tools. Абонемент має окремий журнал відвідувань; зміна заняття не списує його двічі, скасування коригує тільки пов’язаний запис. Це опис продуктового напряму, а не готовий дозвіл на нову схему даних або код.
