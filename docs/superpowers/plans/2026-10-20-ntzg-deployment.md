# План розгортання SciSense на MS-WEB Server

Дата: 2026-10-20, Europe/Kiev. Статус: проєкт плану до погодження, виконання не починалося.
Goal: `objective_e45aa8ac1aa3`; основний внесок G08, перевірки G04/G05/G07/G11. Доручення Юрія: «Тепер підготуй план розгортання додатка на нашому MS-WEB Server під доменом ntzg.pp.ua».

## Специфікація та межа

Результат майбутнього виконання: погоджений реліз SciSense відкривається на `https://ntzg.pp.ua` через Cloudflare з MS-WEB Server, має робочі HTTPS, прямі маршрути, Google-вхід, збереження та перевірений відкат; серверні сусіди не постраждали. Публікація конкретного релізу, приватний пілот і приймання продукту мають окремі докази.

Обсяг (повний перелік): окремий сайт/корінь/користувач у xCloud; статична React-збірка; DNS/HTTPS для цього домену; дозволений домен Firebase Auth; правила маршрутів і кешування; контрольований артефакт/реліз; залежність від готового API голосу й фото; перевірки та відкат. Ця сесія створює тільки документи.

Поза обсягом (повний перелік): перенесення Auth/Firestore у MariaDB або іншу БД; переписування React/CRA; перенесення Worker у Node.js на VPS; встановлення WordPress, Docker чи нового сервера; зміна сусідніх сайтів, загального firewall або default TLS за банером xCloud; платні послуги/API, публікація, приватний пілот чи новий автоматичний deploy без окремого дозволу.

Припущення до погодження (повний перелік):

- Власний сервер роздає інтерфейс; Firebase Auth/Firestore лишаються чинними сервісами. Це рекомендація для цього релізу, не вже погоджена міграція архітектури.
- Повний реліз включає голос/фото і виправлення доступу G04. Поточний main не обирається релізом лише тому, що його тести зелені.
- До готовності продукту допустима лише технічна сторінка без Firebase/AI і приватних даних, якщо Юрій окремо дозволить підготовку live-сайту.
- Перший випуск ручний за точним SHA. Push-to-deploy вимкнено; merge документації не публікує сайт.
- Базовий TLS-вибір: Cloudflare Origin CA на origin, публічний сертифікат Cloudflare на edge, режим Full (strict). Пряме відвідування origin браузером не є підтриманим способом входу.

## Вхідний пакет релізу (повний перелік)

Власник розгортання отримує від реалізації голосу/доступу один узгоджений пакет:

- app SHA, Worker SHA та rules SHA; версію схеми запису; точні lockfiles і Node/npm; зелений CI та відомі дефекти. Для одного репозиторію бажано один інтегрований app/Worker/rules SHA. Номер версії 1.6.0 сам по собі не ідентифікує реліз.
- Виконані автоматизовані перевірки G02/G03/G04/G06, доступні Vxx, класифікацію npm audit за досяжністю. Локальні 86 тестів голосової гілки, 12 Worker, 17 emulator і 25 браузерних сценаріїв є свідченням роботи іншої сесії, а не перевіркою майбутнього SHA.
- Production-конфігурацію Worker готує виконавець релізу разом із власником API-блоку: project, UID allowlist, origins, endpoint, моделі, тарифи, ліміти, бюджет, прив’язку Durable Object. Юрій погоджує акаунти, медіа й витрати перед live. Тільки після цього виконавець розгортання має право встановити цей пакет. Якщо одного поля/доказу немає, крок API зупиняється.
- Матрицю сумісності та порядок переходу старих writers. Перелік чинних хостів, версій клієнта, Worker/rules і способів запису складається до модифікації live.
- Непублічний реєстр доступів/шляхів/бекапів/власника відкату; у Git лише назви параметрів і знеособлені докази.

## Послідовність виконання (повний перелік)

### 1. Передстартова інвентаризація, тільки читання

Відновити авторизацію Cloudflare MCP через UI. Перевірити xCloud-доступ із Keychain або чинної авторизованої сесії, не позичати `filler-xcloud`. Зіставити MS-WEB Server із погодженою адресою; перевірити 3 наявні сайти, їхні домени, stack, site users, права, дисковий запас, vhost/docroot, бекапи й поточні HTTP/TLS-еталони. UUID, порт SSH, login та шляхи брати з фактичної відповіді, не вгадувати. У Cloudflare перечитати фактичні A/AAAA/CNAME для ntzg.pp.ua, proxy status, CAA та правила routing; зіставити target із погодженим origin. Самі NS і публічні proxy IP не доводять правильного target.

Переглянути xCloud preview для Static: домен, спосіб створення, корінь, що панель перезаписує, наявні runtime й поточний тариф. Не запускати creation endpoint. Якщо потрібні витрати, додатковий пакет чи глобальна зміна сервера, винести конкретне рішення окремо. За API використовувати лише документований dry_run, перевірити `would_create`, не трактувати його як створений сайт.

Ізоляція: локальні fixtures/emulators для коду; перед серверною репетицією окремий тестовий vhost і site user з власним коренем, без production Firebase та без провайдерних ключів. Його тимчасовий hostname і TLS погоджуються разом із конкретним створенням. Якщо такої ізоляції немає, не імітувати збої на робочому домені чи сусідах.

Артефакт: локальний інвентар і resolved configuration без секретів, перелік ще відсутніх доступів. Модель: Codex, ризик низький, жодних мутацій. До наступного кроку потрібне погодження конкретних site/domain/path/операцій.

### 2. Підготувати сайт і HTTPS після дозволу на інфраструктуру

Окремий xCloud Static vhost для ntzg.pp.ua, власний site user і корінь. На першому етапі тільки перевірена технічна сторінка без SDK Firebase, API, форм або приватних даних. Не підключати до нового домену існуючий чужий сайт. Не змінювати серверний default vhost/certificate. До дозволу показати точний DNS-diff: наявний proxied A лишається, якщо target правильний; змінюємо тільки помилковий target або доведений конфлікт. AAAA додаємо лише для перевіреного IPv6 цього origin; CNAME/AAAA не видаляємо навмання. Після дозволеної правки перечитати записи через API й авторитетні DNS; інші записи не змінювати.

Параметри продуктового артефакту: Node 24.11.1, npm 11.x, `npm ci`, `npm run test:ci -- --runInBand`, `npm run build`, вихід `build/`. `npm start` є dev-сервером і не запускається у production. У режимі Static немає process start command/публічного Node-порту; SSR і Hybrid не вибираємо. Вихідний repo, .git, .env, node_modules та приватні матеріали не є web root.

На origin згенерувати приватний ключ/CSR через підтриманий секретний механізм, не виводити ключ у чат/логи; встановити Origin CA з SAN ntzg.pp.ua у цьому vhost. Ключ лише у захищеному сховищі/непублічному TLS-каталозі з вузькими правами. Перевірити SNI, строк і chain з кореневим Origin CA; лише потім встановити Full (strict) для цієї зони. Edge Universal SSL перевірити окремо звичайним HTTPS-клієнтом без `-k`. Увімкнути одне узгоджене HTTP→HTTPS перенаправлення й перевірити відсутність циклу.

Артефакт: snapshot конфігурації цього сайту до/після, технічна сторінка й TLS-доказ. Будь-який потрібний привілейований reload має окремо названий обсяг і дозвіл; не використовувати sudo автоматично. Після reload повторити еталон сусідів. Модель: Codex, ризик високий через спільний сервер.

### 3. Підготувати збірку, маршрути й процедуру перемикання

Від дозволеного інтегрованого SHA у чистому середовищі виконати встановлення/тести/build. Зафіксувати public Firebase config, API URL, Node/npm, lockfile і контрольні суми. `REACT_APP_*` потрапляють у JS, отже містять тільки публічні налаштування. Серверні ключі не додаються до frontend env. Для релізу заборонені emulator hostname/порти та `REACT_APP_USE_EMULATORS=true`.

Рекомендована структура всередині перевіреної теки сайту: `releases/<release-id>/public/`, `current` → готовий реліз, попередній безпечний реліз зберігається. У <release-id> входять app SHA й хеш конфігурації/артефакту, бо різні env одного SHA дають різні збірки. Фактичний docroot налаштувати на `current/public`, тільки якщо інвентаризація й репетиція довели підтримку symlink та відсутність його перезапису панеллю. Спочатку upload у тимчасовий каталог, звірка SHA256, права, непорожній index, усі ресурси, потім атомарне перемикання pointer. Якщо xCloud закріплює фізичний шлях і не підтримує таку схему, цей блок зупинити та погодити точний підтриманий механізм; не підміняти його `rsync --delete` по живому кореню.

Відкриті вкладки можуть дозавантажувати старі JS/CSS після перемикання. У новому публічному дереві зберегти hashed assets попереднього безпечного релізу або надати перевірений спільний каталог цих файлів; сам факт збереження окремого releases/ цього не вирішує. Репетиція: вкладка старої версії, перемикання, пізнє завантаження ресурсу без 404. Початковий політичний термін збереження: весь пілот плюс попередній безпечний реліз; прибирання окремо після оцінки диска, без фонової задачі цією сесією.

OLS-правила налаштовуються лише у цьому vhost. Відповіді для `/`, `/trainer`, `/trainer/client/<test-id>` повертають index.html; наявні файли віддаються як файли, відсутні `.js/.css`, `/api/*`, `/.git/*`, `/.env` не переписуються в HTML. Не копіювати mod_headers у .htaccess навмання: OLS має окремі правила для rewrite й заголовків. Перевірити Enable Rewrite/Auto Load і необхідність керованого reload.

Заголовки: index.html і SPA fallback `Cache-Control: no-store`; хешовані JS/CSS `public, max-age=31536000, immutable`; нехешовані manifest/icons `no-cache`. На Cloudflare і xCloud вимкнути для цього сайту full-page/Cache Everything/примусовий Edge TTL; API не кешується. Не змінювати глобальні кеші сусідів. Permissions-Policy не блокує камеру/мікрофон same-origin; COOP/CSP не додаємо шаблоном, який ламає Google popup чи наявні CDN.

Артефакт: незмінний release bundle, маніфест і перевірена на тестовому vhost процедура publish/rollback. Модель: Codex + незалежне рев’ю процедури запису, ризик високий. Усі команди зміни файлів готуються після реальних шляхів, не виконуються з цього плану.

### 4. Підготувати Firebase і API як узгоджений пакет

Після точкового дозволу додати тільки ntzg.pp.ua до Firebase Auth Authorized domains, перевірити чинні referrer/API restrictions публічного web key й додати новий origin за потреби, зберігаючи старі дозволені хости. `authDomain` лишається `nutrition-tracker-ua.firebaseapp.com`, вхід через popup. Не міняти authDomain на ntzg.pp.ua без окремо спроєктованих auth helper routes. До публікації виконати репетицію на окремо погодженому тестовому hostname із тестовими акаунтами та відповідним тимчасовим authorized domain. Саме ntzg.pp.ua перевірити на телефоні після дозволеної публікації у кроці 6; цей результат не є передумовою дозволу на першу публікацію. Popup block/cancel має давати зрозумілий стан. Якщо потрібен redirect login, це окрема зміна за офіційною схемою reverse proxy `/__/auth/*`, не HTML fallback.

Worker: виконавець отримує пакет із розділу вище; конкретний endpoint на Cloudflare фіксується в release manifest, а ALLOWED_ORIGINS містить рівно `https://ntzg.pp.ua` і лише окремо погоджені тестові origins. FIREBASE_PROJECT відповідає реальному токену, ALLOWED_UIDS містить погоджені тестові акаунти. Ключі через stdin у Cloudflare secrets, Durable Object/тарифи/моделі/бюджет лише за окремим дозволом. `LIVE_ENABLED=false` до цього дозволу. Жодного реального тесту через emulator-обхід JWT або чужий клієнтський ключ.

До публікації перевірити токен/UID, CORS, timeouts, 401/403/429, серверні ліміти та відсутність медіа в логах. G04 виправляється в окремому погодженому блоці доступу; в цьому плані воно є вхідним гейтом. Не виконувати `firebase deploy` без `--only`: інтерфейс на VPS, Firestore rules і старий Hosting мають окремі дозволені дії.

Артефакт: app/Worker/rules/config manifest і свіжі докази для узгодженого набору. Модель: Codex + незалежне рев’ю доступу, ризик високий. Публічний API та його витрати не вмикаються самим погодженням документа.

### 5. Перевірити перехід зі старих клієнтів

Матриця до релізу (повний перелік):

| Поєднання | Обов’язковий результат |
| --- | --- |
| Поточний клієнт Firebase Hosting / стара вкладка + нові rules/схема | Старі небезпечні записи відхилено сервером або сумісність без втрат доведена тестами |
| Новий клієнт + старі rules, поки нові ще поширюються | До підтвердженої безпечної серверної політики запис не дозволяється; поведінка й відновлення чернетки перевірені |
| Новий клієнт ntzg + нові Worker/rules | Усі основні сценарії й G04 пройдені |
| Попередній безпечний клієнт + Worker/rules, що залишаться після rollback | Доведений read-write без стирання нових fields/markers/revision |
| Непогоджений старий Worker + новий клієнт | Не обирається конфігурацією; помилковий endpoint не завершується тихим успіхом |

Порядок: спершу репетиція матриці на стенді; після окремого дозволу адресний backup і застосування погоджених rules та Worker; потім перевірка фактичних дозволів/заборон у новій сесії та старому активному listener; лише тоді дозвіл нового клієнта на запис і контрольоване оновлення дозволених frontend-хостів. Команда deploy не підтверджує поширення правил: за документацією Firebase нові запити/listeners можуть оновлюватися до хвилини, активні listeners до десяти хвилин. Саме очікування десяти хвилин теж не є доказом: потрібні успішні позитивні й негативні перевірки. Якщо поширення не підтверджене, лишається заздалегідь погоджений безпечний перехідний стан, публікацію/запис не відкривати. Далі звірити записи й відключення застарілих маршрутів. Якщо необхідний несумісний перехід, готується окреме коротке вікно обслуговування із серверним блокуванням старих writers та захистом незбережених даних; до його погодження stop. Закриття вкладок, зміна DNS чи приховування старого Firebase Hosting самі по собі не припиняють прямі Firestore-записи.

Старий Hosting не вимикати наперед, але й не оголошувати безпечним fallback без цієї матриці. Якщо його потрібно оновити до того самого перевіреного bundle або перевести на maintenance, це вказати в конкретному дозволі на cutover. Міграція даних і відкочування rules до відомо небезпечної версії не входять у автоматичний відкат.

Артефакт: заповнена матриця, точний порядок app/Worker/rules і дозволених дій старого хоста, відповідальний за rollback. Модель: Codex + рев’юер, ризик високий.

### 6. Погодження релізу та публікація

Показати Юрію конкретні SHA/артефакт, репетицію D01–D07 у тестовому середовищі, стан G04, список live-змін, отримувачів медіа/бюджет, очікуване вікно та відкат. До дозволу: domain TLS на технічній сторінці, цілісність артефакту, G04/emulator, тестові маршрути/вхід/API та репетиція відкату. Після публікації: остаточне підтвердження D02/D03/D04/D05 на ntzg.pp.ua і порівняння сусідів D07. До цього вони позначені «тестовий стенд пройдено; цільовий домен pending», а не повний PASS. Публікація тільки після його дозволу. Готовність до пілоту не вимагає, щоб пілот G09/G10 уже був пройдений: вони перевіряються після дозволеного випуску.

Зняти адресні бекапи vhost/TLS-конфігурації без відкритих ключів, Auth allowlist, правил/Worker settings і поточного релізу. Перед зміною rules/даних мати перевірений відповідний backup; збереження лише frontend не є backup Firestore. Інфраструктурні витрати й привілейовані операції мають бути названі в дозволі. Завантажити готовий bundle, звірити manifest, перемкнути тільки цей сайт, перевірити поточні DNS/HTTPS/routes/ресурси, потім дозволені синтетичні login/read-write/voice-photo сценарії.

Підсумковий доказ: actual URL + release-id + контрольні суми + час + results. HTTP 200 без збігу артефакту не є deployment. CI success, merge й відповідь xCloud 202 теж не є deployment. Модель: Codex, ризик високий; виконання покрокове з названими гейтами.

### 7. Відкат і завершення

Тригери відкату (повний перелік): TLS/5xx; відсутні ресурси; неможливий вхід; чужий доступ; втрата/дубль запису; неправильна дата/сума; неконтрольований API-виклик/витрати; регресія сусіднього сайту після дозволеної операції.

- Якщо є попередній сумісний безпечний реліз: зупинити нові API-виклики/публікації, повернути pointer, звірити його хеши та тільки пов’язані параметри. Повторити TLS/routes/login/read-write. Worker відкотити лише за перевіреною матрицею; не скидати Durable Object бюджет/ліміти й не послаблювати G04.
- Якщо це перше розгортання: повернути заздалегідь перевірену технічну сторінку, API вимкнути. Перевірка цього сценарію: HTTPS 200, видимий текст обслуговування, немає app bundle/Firebase/AI-запитів. Login/read-write тут не очікуються. Активні старі вкладки зупиняє погоджений серверний захист writers, сама сторінка цього не гарантує.
- Збірка/upload не завершились: не перемикати current, лишити чинний реліз. CF purge лише точково для цього домену за потреби; без загального cache flush. DNS/NS не повертаємо на парковку і не вимикаємо проксі з Origin CA.
- При регресії сусідів відновити тільки конфігурацію, змінену цією операцією, та застосувати погоджену процедуру reload. Не відновлювати весь сервер поверх нових даних.

Після успішної перевірки зафіксувати actual release, час, джерела, відкат, строк сертифіката й відповідального. Пілот, приймання Юрієм і майбутня автоматизація є окремими етапами; моніторинг/нагадування цим планом не створюються. Модель: Codex + незалежний перевіряльник, ризик високий для сумісності запису.

## Офіційні джерела

Context7 resolve-library-id повернув вичерпану місячну квоту. Заміна: первинні документи, прочитані 2026-10-20; можливості конкретного акаунту/сервера перевіряються окремо.

- [xCloud: Node.js та Static](https://xcloud.host/docs/how-to-deploy-a-node-js-application/): Static не потребує постійного Node-процесу, build і serving налаштовуються окремо.
- [xCloud: Git deployment API](https://xcloud.host/docs/deploy-git-projects-with-xcloud-public-api-and-mcp/): dry_run/would_create, явні параметри, idempotency; queued не дорівнює deployed. Приклади секретів у argv з документації не копіювати.
- [xCloud: сумісність stacks](https://xcloud.host/docs/web-server-compatibility-for-different-applications/): Node.js доступний на OLS.
- [OLS: rewrite](https://docs.openlitespeed.org/config/rewriterules/): керування на рівні vhost, Auto Load, потреба застосувати конфігурацію.
- [Cloudflare: Origin CA](https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/) і [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/): перевірка origin certificate, довіра CA, обмеження direct access й облік строку.
- [xCloud: Let’s Encrypt](https://xcloud.host/docs/install-lets-encrypt-ssl-certificate/): окремо перевірити випуск/поновлення за проксі; старий приклад вимагає proxy off.
- [Firebase: поширення правил](https://firebase.google.com/docs/firestore/security/get-started#deploying_rules): затримка для нових та активних listeners, необхідність перевірки після дозволеної публікації rules.
- [Firebase: popup/redirect на зовнішньому хості](https://firebase.google.com/docs/auth/web/redirect-best-practices) і [Google sign-in](https://firebase.google.com/docs/auth/web/google-signin): authorized domains, збереження popup або окрема схема auth helper proxy.
