# SciSense: сказати, сфотографувати, додати

Дата: 2026-10-20. Статус: проєкт специфікації до технічного погодження.
Goal `objective_e45aa8ac1aa3`: G02, G03, G05, G07, G08, G11; основна картка `card_a0a505e98d94`.

## Мета й підтверджені рішення

Людина записує з’їдене без ручного пошуку й набору БЖВ. Юрій підтвердив: запис голосу в додатку з головного екрана; фото упаковки разом із голосом у першому етапі; коротке прев’ю та одна кнопка «Додати». Сценарій: «випив цей кефір, 200 грамів» → фото назви й етикетки → готовий рядок продукту з перерахованими значеннями → підтвердження → прийом збережено.

Це замінює обмеження старої серпневої специфікації на клавіатурне диктування. Старі особисті матеріали не копіюються у публічний Git.

## Варіанти

| Варіант | За | Проти |
| --- | --- | --- |
| A. Клавіатурне диктування й текстовий парсер | Частина коду вже є | Не виконує вимогу запису в додатку й фото |
| B. Запис + фото у спільній чернетці, готові API через наявний Worker | Відповідає сценарію; повторне використання UI, авторизації й збереження | Потрібні API доступи, перевірка телефона й контроль витрат |

Рекомендовано B. A не виконує пряме рішення Юрія; C не дає виправданого виграшу для цього етапу.

## Потік (повний перелік)

1. На головному екрані щоденника, без меню й прокручування, є доступна кнопка мікрофона. Показано цільові дату й прийом; вони фіксуються для чернетки при старті. На вході показаний день має явний mealsDateKey; для нового порожнього щоденника це локальна сьогоднішня дата, а не programDay. targetDate береться з показаного mealsDateKey.
2. Натискання запитує дозвіл і починає запис у додатку. Видно таймер і «Зупинити». Українське та російське мовлення підтримуються. Ніякого обов’язкового переходу до клавіатури.
3. «Зупинити» завершує звук і запускає розпізнавання. Після цього доступні «Сфотографувати» та, як запасний шлях, вибір фото. Фото необов’язкове для кожного прийому, але сама можливість є в першому етапі. Можна додати 2 кадри: назву і таблицю харчових значень тієї самої упаковки.
4. API поєднує сказану кількість із продуктом/етикеткою. Якщо фото належить уже розпізнаному кефіру, уточнюється цей рядок. Для кількох можливих рядків показати короткий вибір; не додавати дублів і не прив’язувати фото навмання.
5. Прев’ю показує назву, кількість з одиницею, ккал/БЖВ для порції, джерело та позначку оцінки. Доступні виправлення тексту, кількості, видалення рядка й повторне фото. Кнопка «Додати» є єдиним підтвердженням запису. Окрема обов’язкова кнопка «Розібрати» не потрібна.
6. Після підтвердження виконати один узгоджений запис у зафіксовані дату/прийом; повідомити успіх лише після підтвердження сховища. При помилці чернетка залишається. Повтор натискання/запиту не дублює їжу.

## Джерела та кількість (повний перелік)

- Читабельна етикетка конкретної упаковки має пріоритет над загальним каталогом. Фото назви саме по собі не є доказом її БЖВ.
- Наступні джерела: точний продукт у перевіреній базі за штрих-кодом/назвою, далі відповідний продукт каталогу. Уже наявний Open Food Facts адаптер можна використати після перевірки одиниць і відсутніх полів. Не прирівнювати відсутнє поле до нуля.
- Якщо точного продукту немає, для однозначно зрозумілої їжі та кількості допускається оцінка зі значень загального каталогу або моделі. Джерело «Оцінка моделі» показується прямо; бренд і точність етикетки не приписуються. Якщо незрозуміло, яка це їжа, що означає кількість або яка основа чисел, потрібне уточнення; самі вигадані числа проблему не закривають.
- «Додати» доступна, коли є хоча б один рядок і кожен має назву, узгоджену кількість/одиницю, повний набір ккал/Б/Ж/В та джерело. Відсутнє значення не нуль. Неповний рядок або нерозпізнаний фрагмент треба уточнити чи явно вилучити з чернетки; частково розібраний текст не відкидається мовчки. Вилучення явно показано до підтвердження. Виправлення БЖВ вручну можливе як запасний шлях, але не зараховується в успішну метрику G09.
- Фотографія уточнює харчові значення, а сказані «200 грамів» є спожитою кількістю. Маса упаковки не замінює порцію. Розрізняти значення на 100 г, 100 мл, порцію та всю упаковку.
- Чернетка має явні quantity/value/unit і nutritionBasis/value/unit. Усі числа скінченні та невід’ємні; кількість більша нуля. Перерахунок і округлення виконує код. Непорівнювані г/мл не перетворюються без підтвердженої густини/основи; попросити одиницю/кількість, сумісну з етикеткою, або показати оцінку як окремий вибір.
- На записі зберігаються itemId, назва, кількість/одиниця, джерело значень, nutritionBasis із кількістю/одиницею, ккал/Б/Ж/В на цю основу, погоджений коефіцієнт raw/cooked за потреби та ознака оцінки; медіафайли не зберігаються разом з прийомом. Для старих записів без нових полів залишається поточна грамова поведінка. Список прийому, підсумки та звіт показують однакову одиницю; raw/cooked перерахунок застосовується тільки за визначеною основою. Новий item є самодостатнім: редагування кількості, підсумки й звіт рахуються з його основи, без повторного пошуку за назвою в каталозі. Калорії джерела не замінюються формулою 4/9/4. Для legacy без наявних ккал дозволений однаковий в усіх представленнях похідний результат із явним джерелом розрахунку; особисті цілі не змінюються.
- Фікстура без персональних даних: «Тестовий кефір», етикетка на 100 г: 60 ккал, Б 3.2, Ж 3.4, В 4.2; голос 200 г. Очікується 120 ккал, Б 6.4, Ж 6.8, В 8.4; у сховищі один рядок. Друга синтетична етикетка: на 100 г 53 ккал, Б 2.9, Ж 2.5, В 4.0; 200 г дають 106 ккал, Б 5.8, Ж 5, В 8 в прев’ю, рядку, Header і звіті. Формула 4/9/4 дає інше число і не замінює 106. Редагування першого збереженого рядка з 200 до 250 г дає 150 ккал із тієї самої етикетки. Це синтетичні тестові числа, не харчова рекомендація.

## Межі реалізації та API

Повторно використати наявний Cloudflare Worker, Firebase Auth, структуру прев’ю й шлях запису після цільового перенесення з feat/voice-input на свіжу main-базу. Не зливати всю стару гілку автоматично.

Аудіо: getUserMedia + MediaRecorder; MIME обирається через isTypeSupported, перевіряється на реальному телефоні. Записаний файл надсилається на автентифікований Worker, який викликає готовий transcription API. Пропозиція: OpenAI file transcription, документований gpt-transcribe; прямий ключ у браузері заборонений. Для зображення й структурованого розбору продовжити адаптер Anthropic. Конкретний підтримуваний ID моделі та API-акаунт фіксуються до реального виклику; старий hardcoded ID у коді не є доказом доступності. Зміна цього конфігураційного значення не дозволяє міняти архітектуру чи бюджет.

Перший етап не включає realtime-сесію, власну STT-модель, OCR-сервер, фотовизначення ваги тарілки або нову медичну логіку. Ручне введення є запасним шляхом; воно не зараховується як успіх голосового сценарію.

## Чернетка, збої та приватність (повний перелік)

- Стан: idle → permission → recording → processing → preview → saving → saved; error/retry повертає ту саму актуальну чернетку. Кожна чернетка має sessionId, targetDate, targetMeal і revision; кожна зміна тексту, фото, кількості, одиниці, вибору джерела, прив’язки фото, цілі або складу рядків збільшує revision. Пізня відповідь іншої session/revision ігнорується. Зміна кількості/одиниці з відомим коефіцієнтом, видалення рядка та цілі дає тільки локальний перерахунок; текст, нове фото або нова прив’язка фото запускає новий розбір відповідної актуальної версії. Ручні поля не перезаписуються результатом попереднього запиту.
- День завантажується з mealHistory/mealsDateKey, порожній день не заповнюється вчорашнім users.meals. Старий root-snapshot без дати не можна мовчки віднести до сьогодні: зберегти без змін і попросити одноразово підтвердити його дату до перенесення/перезапису. Новий users mirror має власний mealsDateKey. Авторитетним є денний документ. Зміна локальної доби не змінює дату вже завантажених meals. При targetDate ≠ mealsDateKey перед «Додати» явно показати вибір: повернутися до цільового дня або перенести чернетку до показаного. Жодного дублювання в обидва дні. Після входу без змін не запускати snapshot-запис.
- Повторне відкриття не приймає результат закритої сесії. Перехід дати не переносить їжу мовчки: ціль чернетки лишається видимою; зміна цілі тільки явною дією до підтвердження. Signout очищає приватний стан.
- Закриття під час запису/обробки скасовує запити й зупиняє всі власні tracks; object URLs звільняються. Відповідь getUserMedia після закриття також негайно зупиняє tracks. Відмова камери/мікрофона дає конкретне повідомлення, а не порожній запис.
- Чернетка та дозволені повтори живуть у поточній сесії; перезавантаження не обіцяє збереження аудіо/фото. Навмисний вихід із незбереженим результатом має підтвердження. Не вести приховану медіаісторію.
- Для commit використати стабільний submissionId, атомарну owner-зміну й захист від повтору на рівні сховища. Однаковий submissionId повторно не додає рядків навіть у двох сеансах; дві незалежні чернетки з різними ID є двома навмисними записами, навіть якщо їжа однакова. Спільної хмарної медіачернетки немає. Невизначений timeout перевіряється за submissionId перед повтором; UI не оголошує невдалий запис, якщо результат ще невідомий.
- Запис: Firestore transaction читає owner-документ і mealHistory цільової дати; marker submissionId у цьому денному документі та нові items записуються атомарно з потрібною поточною проєкцією users. Повтор із тим самим ID і іншим payload відхиляється як конфлікт. Кожен item має стабільний ID. Всі записи їжі, включно з ручними та автозбереженням, проходять один адаптер із ревізією дня; застарілий повний snapshot не замінює нові items, а конфлікт повертає актуальний день для явного повтору. Окремі поля submissionMarkers і revision не видаляються/не обнуляються автозбереженням. Денний документ не замінюється цілком через setDoc без merge; адаптер змінює тільки перелічені бізнес-поля й ревізію, зберігаючи маркери. users projection та mealHistory пишуться в одній транзакції. Перший запис старого дня без revision трактує її як 0, без масової міграції. Callback транзакції не змінює React state, не звертається до API й може повторитися; стан оновлюється після commit. Offline лишає чернетку, не створює повідомлення про успіх. Перед релізом G08 окремо перевіряє старий відкритий клієнт і блокує несумісний старий запис або вимагає контрольованого оновлення; локальна фаза не дозволяє змішане production-розгортання.
- Worker перевіряє Firebase ID token, UID, origin, тип, розмір і схему до зовнішнього виклику. Потреба в наявному дозволеному джерелі Origin не замінює авторизацію. Для лабораторії окрема конфігурація без production-даних.
- Початкові ліміти-пропозиції: голос до 90 с/10 MiB; до 2 фото JPEG/PNG/WebP по 5 MiB, після перевіреної нормалізації орієнтації; до 20 рядків їжі. Непідтримуваний формат не надсилається мовчки. Перевірити реальне фото iPhone/Android; за потреби декодування до підтримуваного формату входить у цей блок.
- Незалежні таймаути: після 20 с очікування медіадозволу показати пояснення та скасування, не називати це відмовою користувача; 45 с для окремого upstream, 60 с для клієнтського запиту. Аудіотранскрипція й розбір є окремими запитами, тому два послідовні upstream не ховаються під одним 60-секундним таймером.
- Одиниця квоти: один фактичний виклик платного API; резервування до його запуску. Пропозиція: 6 викликів/ковзні 60 с та 30/добу UTC на UID, максимум 2 одночасні; усі ручні повтори враховуються, автоматичні retry SDK вимкнені. Голос → транскрипція + текстовий розбір витрачає 2; два послідовні уточнення фото ще 2; локальне виправлення кількості 0. Фото можна додавати разом одним запитом. Скасування після початку upstream не повертає витрачений слот.
- Обраний механізм квот для невеликого пілоту: один Cloudflare Durable Object із SQLite, атомарним резервуванням UID-квоти та загального бюджету пілоту; лише лічильники/терміни/непрозорі request IDs, без медіа й тексту їжі. Restart зберігає лічильники, несправний лімітер блокує платний виклик. Резерв вартості обчислюється за зафіксованими перед live-тестом тарифами, лімітами input/output і аудіо; непідтверджена вартість залишає повний резерв. Загальна сума має бути явно погоджена й задана в конфігурації; відсутня сума закриває live-режим. Новий binding/міграція спочатку перевіряється локально; реальне створення інфраструктури та будь-яка зміна тарифного плану мають окремий live-гейт. Не підміняти це пам’яттю процесу або браузерним лімітом.
- API-ключі тільки у проєктному secret store, без запозичення ключів інших продуктів. Сирі аудіо/фото/розшифровки не пишуться в логи, аналітику, Git або Firestore. Політика зберігання у провайдерів і бюджет погоджуються до надсилання реальних матеріалів; відсутність нашого сховища не є обіцянкою нульового зберігання у провайдера.

## Вимірювання пілоту

Пропозиція для G09: attemptId створюється до запиту дозволу при кожному натисканні мікрофона для нового/повторного запису або при явному повторі невдалої API-обробки. «Зупинити», додавання фото до актуальної чернетки й локальні виправлення не створюють нової спроби. Невдача попередньої спроби зберігається; нова може містити parentAttemptId. Приклад тиша → повторний запис → збереження дає 1 успіх / 2 спроби. Permission deny, закриття й offline до Worker теж у знаменнику; запис з невизначеним commit спочатку reconciles submissionId, повтор читання результату не нова API-спроба.

Облік лише у погодженому режимі пілоту: компактний локальний IndexedDB журнал з attemptId, opaque submissionId, часами/тривалостями, лічильниками дій, hasPhoto, manualSearch/manualPfc, status (started/saved/abandoned/error/unknown). Без назви їжі, аудіо/фото, розшифровки, БЖВ-значень, email або UID. started без продовження після reload переходить в abandoned; unknown перевіряється за marker, не стає автоматично успіхом. Журнал стартує до дозволу й переживає reload; якщо запис недоступний, пілот позначений непридатним до оцінки, спроби не рахуються вибірково. Вивантаження для приймання містить лише псевдонімні ID, результати та тривалості; локальний журнал видаляється після приймання або через 30 днів. Успіхом є лише правильний повний прийом, який перевірив учасник пілоту; явно вилучений нерозпізнаний фрагмент дозволяє часткове збереження, але не зараховується як повний успіх. Не додавати загальну аналітику для всіх користувачів.

Канал телефона в лабораторії: локальний HTTPS на dev-сервері із сертифікатом, якому власник явно довірив на тестовому пристрої, reverse proxy до Firebase emulators і wrangler dev; demo project, тестові акаунти та підставний upstream. Production project/hosting недоступні цій конфігурації, без публічного tunnel за замовчуванням. Встановлення довіри на телефоні виконує власник; якщо недоступно, телефонна перевірка лишається pending, не підміняється desktop. Усі server-компоненти локальні; V09 додає зовнішні API тільки після дозволу.

Команди-пропозиції: `npm run test:voice-photo` (V02–V07, контракти й emulator); `npm run test:voice-photo-ui` (V01/V03/V05/V06/V08, ізольований browser launcher); наявні `npm run test:ci -- --runInBand`, `npm run build`. Нові scripts ще відсутні. Перший дозволений блок створює їх і демонструє реальні FAIL на старій реалізації; відсутній script не є червоним тестом. Лабораторія не доводить V09 і G09 без погодженого реального прогону.
