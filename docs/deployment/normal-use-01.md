# NORMAL-USE-01: звичайне сімейне використання тренера

Дата: 2026-10-27. Goal objective_e45aa8ac1aa3; G02/G05/G06/G07/G08/G11, приймання pending.

## Підстава й межа

Користувач прямо доручив прибрати тестове обмеження, щоб він із дружиною користувався тренером; після повторної помилки доручив завершити виправлення, перевірити текст/голос/фото, стани UI й скріншоти. Це змінює попередній гейт8turn/24POST. Нових модельних ключів, платного API fallback, ресурсів CPU/RAM або глобальних прав не додаємо. Публікація потрібного виправлення погоджена в цій сесії. Це виконання конкретного доручення в наявному сценарії, без нового продуктового дизайну чи зміни приватності.

## Рішення

- Загальні caps8turn/24POST прибираються для обох верифікованих профілів, не замінюються іншою добовою квотою.
- Історичний accounting scope зберігається, рахівники/receipts не видаляються і не обнуляються.
- Одна фізична обробка має захист від циклу:12physicalPOST/90с, одна модель,2CPU/2GiB/swap0, черга4. Це не квота кількості звернень. Підпискові обмеження провайдера застосунок не змінює.
- Зміна охоплює Node/Python IPC, kernel timer C, runtime/activation policy hash та exact legacy4→8 Native config upgrade. Binary timer береться лише з перевіреного CI пакета або компілюється з точного погодженого C source; SHA в трьох role configs звіряється.
- Помилка не називається обривом з’єднання без доказу. Unknown не пересилається автоматично. Користувач може зупинити обробку та повернути текст перед новим явним Send.
- Голос: явний старт, зупинка, прослуховування/текстове прев’ю, редагування/скасування; текст/фото зберігаються. Невдале STT зберігає локальний запис для явного повтору. Add завжди окрема підтверджена дія.
- Стару застряглу спробу можна лише адресно скасувати після fresh snapshot, через guarded control із перевіркою фізичного завершення її виконавця. Текст/native history/accounting зберігаються; жодного автоматичного save або повтору невідомого input.

## Виявлений під час реальної проби Native FIFO

Після публікації1.9.3 новий контрольний вхід не виконав жодного POST: старий Native unknown залишався головою FIFO, хоча його App-turn уже був cancelled. Публічний cancel завершував лише App-стан. Наступна доробка в межах погодженого виправлення: окремий guarded control за UID/input/Native binding, queued скасовується через prompt.cancel, unknown через prompt.resolve_unknown із точним поколінням. readNative залишається лише для читання. Maintenance не отримує права автоматично вирішувати unknown.

Перед вирішенням unknown усі інші pending мають бути відсутні, інакше дія відхиляється. Для наявного випадку спершу адресно скасувати контрольний queued-хвіст, перечитати terminal/cancelled, лише тоді вирішити стару голову. Жоден старий вхід не надсилається повторно. Lost-ACK/непідтверджене завершення зберігає cleanup-job. Новий явний контрольний запит виконується після такого відновлення, без food save. Потрібні регресії справжньої pinned Native authority, незалежне рев’ю та CI.

## Читання live SQLite під час розгортання

SQLite із mode=ro може створити WAL/SHM. Якщо оператор root відкриває базу іншого користувача, ці файли можуть отримати власника root і зламати наступний запуск служби. У фіксованому однопотоковому операторі перед connect перевіряються власник, звичайний тип файла, nlink=1 і відсутність symlink; euid/egid та групи тимчасово перемикаються на власника бази. Цей контекст охоплює всі запити й close. Початкові права повертаються у вкладеному finally, зокрема після помилки close. Живе WAL не читається з immutable, бо так можна пропустити підтверджені транзакції. Підміна власника готових WAL після root-читання не замінює цього контролю.
